# 第 1 回 Lチカで学ぶ Verilog 作法 — 27MHz は秒よりも速い

> 「定義をきちんと確認することは、いつでも大切なんだ」

## 登場人物

- **ありす** — バックエンド担当。理屈っぽく論理的で、定義から組み立てるのが好き。今回は教える側。
- **桃華** — フロントエンド担当。きらびやかなものに目がない。Verilog はまだ駆け出し。今回は教わる側。

題材は `00_counter/src/led.v` — Tang Nano 9K の 6 個の LED を 0.25 秒ごとに 2 進カウントさせる、小さなプログラム。

## プロローグ

放課後の部屋。机の上に Tang Nano 9K の小さなボードが転がっている。6 つの LED が、ゆっくりと 2 進数を刻んでいる。

「桃華さん」とありすが言った。「この LED、何を表示しているのか、説明できる？」

「えぇ、ありすちゃま」と桃華は得意げに答える。「6 ビットの 2 進カウンタですわ。0.25 秒ごとに +1 されて、64 回で一周しますの」

「ふむ。じゃあ、ソースコードを見せて」

桃華が `led.v` を画面に開くと、ありすは静かにそれを眺めた。

「これを題材に、Verilog の作法を順番に確認しよう」とありすは言った。「動くコードを書けることと、**作法に沿ったコードを書けること**は、別の能力だから」

「お願いいたしますわ」

## § 1. 暗黙の配線 — `default_nettype`

「最初の質問」とありすは指を 1 本立てた。「Verilog で、宣言していない名前を書くと、どうなるか知ってる？」

桃華は少し考えた。「エラーになる…のでは？」

「ううん。**勝手に 1 ビットの wire として作られる**」

「えっ……?!」

「これが Verilog の歴史的な罠なんだ。例えばこう書いたとする」

```verilog
assign ledd = ~led_count;   // 'led' のタイプミス
```

「`ledd` という名前は宣言してないのに、Verilog はこれを 1 ビット wire と解釈する。どこにも繋がっていない、孤立した信号が作られる。**コンパイルは通る。でも LED は光らない**」

「それは……困りますわ」

「だから現代の作法では、ファイルの先頭にこう書くんだ」

```verilog
`default_nettype none
```

「これを書くと、宣言していない名前は **構文エラーになる**。タイプミスはコンパイラが捕まえてくれる」

「タイプミスを赤ペン先生に任せられる、ということですわね」

「いい表現だね」とありすは微かに笑った。「ただし `led.v` には今これが入っていない。これは『次に学ぶべき作法』として記録しておこう」

> **作法 1.** プロジェクトの新規 Verilog ファイルでは、先頭に `` `default_nettype none `` を書く。

---

## § 2. 時間の単位を決める — `timescale`

「次の質問」とありすは続けた。「シミュレーションで `#10` と書いたとき、それは何秒？」

「えっと……10 単位時間？」

「**じゃあ 1 単位時間は何秒？**」

「……」

「答えは『分からない』。なぜなら、Verilog は時間の単位を **ファイル外** で決めるからだ」

```verilog
`timescale 1ns / 1ps
```

「左の `1ns` が時間の単位。`#10` は 10 ナノ秒という意味になる。右の `1ps` は時間精度。シミュレータが内部で持つ最小刻みだ」

「では `1ns / 1ps` なら、`#0.001` と書いたとき……」

「1 ピコ秒として扱われる。精度を超えると丸められる」

桃華は『時計の文字盤と秒針の最小刻み』を思い浮かべた。文字盤が単位、秒針の動く間隔が精度。

「これも合成では無視されるから、ハードウェアには影響しないんだけどね。シミュレーション結果が変わってしまう」

> **作法 2.** シミュレーション対象ファイルでは、先頭に `` `timescale `` を書く。プロジェクト内で統一する。

---

## § 3. 数字に名前を付ける — `parameter` と `localparam`

「桃華さん。この行を見て」

```verilog
else if (counter < 23'd6_749_999)
```

「`6_749_999` という数字、これは何？」

「えっと……27,000,000 ÷ 4 − 1 ですわよね。27MHz クロックで 0.25 秒待つための tick 数」

「正解。じゃあ、もしクロックが 50MHz に変わったら、どこを書き換える？」

桃華は息を呑んだ。「……コード中に散らばっている `6_749_999` を、全部書き換えないといけませんわ。`23'd0` のビット幅も……」

「そう。これが **マジックナンバーの罠**。`led.v` には、こうしておくともっと整理できる」

```verilog
module led #(
    parameter integer CLK_FREQ_HZ     = 27_000_000,
    parameter integer BLINK_PERIOD_MS = 250
) (
    // ... ポート宣言
);
    localparam integer TICK_COUNT = CLK_FREQ_HZ / 1000 * BLINK_PERIOD_MS;
    localparam integer CNT_WIDTH  = $clog2(TICK_COUNT);

    reg [CNT_WIDTH-1:0] counter;
    // ...
    if (counter == TICK_COUNT - 1)
        counter <= 0;
```

「`parameter` はモジュールの外から上書きできる定数。インスタンス化のときに、別の値を渡せる」と、ありすは指でコードをなぞる。「`localparam` は外から上書きできない、ローカルな定数。`parameter` から計算した派生値を入れるのに使う」

「`$clog2` は……?」

「`ceil(log2(x))` の Verilog 関数。`TICK_COUNT` に必要なビット幅を計算してくれる。これでビット幅もハードコードしなくて済む」

「クロック周波数が変わっても、`parameter` 一つ変えれば全部が連動する……ですわね」

「これが **データ駆動** の作法だ。論理を書き換えるのではなく、定数を書き換えるだけで挙動が変わる」

> **作法 3.** マジックナンバーは `parameter` / `localparam` で名前を付ける。クロック周波数のような外部依存値は `parameter` に、その派生値は `localparam` に。

---

## § 4. 「いつ」を決める — クロックエッジと感度リスト

```verilog
always @(posedge sys_clk or negedge sys_rst_n) begin
```

「桃華さん。この一行を声に出して読んでみて」

「えっと……『sys_clk の立ち上がりエッジ、または sys_rst_n の立ち下がりエッジで、以下のブロックを実行する』ですわ」

「正確だね」とありすが頷いた。「Verilog の `always @(...)` は、**カッコの中に書いたイベントが発生したときだけ** 中身を評価する、という宣言だ」

「`@(posedge sys_clk)` だけだと、何が起きますの？」

「クロックの立ち上がりだけに反応する。これが **同期式** の基本形」

「`or negedge sys_rst_n` を足すと？」

「クロックとは独立に、リセット信号にも反応するようになる。これが **非同期リセット** だ」

桃華は紙にスケッチした。クロックの矩形波の上に矢印を立てる。立ち上がりに ↑。

「ハードウェア視点だとね」とありすは続ける。「`@(posedge sys_clk or negedge sys_rst_n)` は、**クロック端子とリセット端子の両方を持つフリップフロップ** を要求している。FPGA の DFF は、ちょうどそういう端子を持っている」

「コードの形が、回路の形を決めている……」

「そう。Verilog は **ハードウェア記述言語** であって、プログラミング言語じゃない。書き方を変えれば、合成される回路が変わる」

> **作法 4.** `always @(...)` の感度リストは、合成される回路を決める。クロック駆動の FF は `posedge clk` を書く。

---

## § 5. リセットの 2 つの流派 — 同期と非同期

「ところで」とありすが言った。「リセットには 2 種類ある、というのは知ってる？」

「2 種類……?」

「**同期リセット** と **非同期リセット** だ。書き分けはこう」

```verilog
// 同期リセット
always @(posedge clk) begin
    if (!rst_n) q <= 0;
    else        q <= d;
end

// 非同期リセット（led.v で使っている形）
always @(posedge clk or negedge rst_n) begin
    if (!rst_n) q <= 0;
    else        q <= d;
end
```

「違いは、感度リストに `negedge rst_n` が **入っているかどうか** だけ」

「効果は……?」

「同期式は『クロックが来たときに、もしリセットが入っていたら 0 にする』。非同期式は『クロックを待たずに、リセットが入った瞬間に 0 にする』」

桃華は考えた。「直感的には、非同期のほうが速くて良いように感じますわ」

「速いのは確かにそう。でも、トレードオフがある」

ありすは表を書いた。

| 観点 | 同期リセット | 非同期リセット |
|------|------------|--------------|
| リセット応答 | クロック 1 サイクル待つ | 即時 |
| メタステーブル | 起きにくい | リリース時に注意必要 |
| FPGA との相性 | 良い（タイミング解析が素直）| 良い（DFF が非同期端子を持つため） |
| ASIC の標準 | 大規模設計で主流 | スタートアップなど一部 |

「FPGA の場合、ベンダーが推奨する流派が分かれている。Xilinx は同期推奨、Lattice/Gowin は非同期も普通に使う。`led.v` は非同期式を採用している」

「どちらが正解、というわけではないのですわね」

「うん。**プロジェクト内で統一する** ことが、何より大事だ」

> **作法 5.** リセット方式は同期 / 非同期のどちらかを選び、プロジェクト全体で統一する。混在させない。

---

## § 6. 「同時」の意味 — non-blocking と blocking

「次は、Verilog で最も誤解されやすい話だ」とありすが言った。「`<=` と `=` の違い」

「ノンブロッキング代入とブロッキング代入、ですわよね」

「概念だけ知っていても、いつ使い分けるかが分からないと意味がない。例を見よう」

```verilog
// 例 A: blocking ( = )
always @(posedge clk) begin
    a = b;
    b = a;
end

// 例 B: non-blocking ( <= )
always @(posedge clk) begin
    a <= b;
    b <= a;
end
```

「桃華さん。クロックエッジの後、`a` と `b` はどうなる？」

桃華は紙に書き出した。「例 A は……`a = b` で `a` が更新されて、その値を使って `b = a` で `b` が更新される。だから `a` も `b` も両方とも、元の `b` の値になりますわ」

「正しい。例 B は？」

「`<=` は……『右辺を全部評価してから、左辺に代入する』ので、`a` と `b` が **入れ替わる** ……ですわ」

「完璧」とありすは満足げに頷いた。「これが **non-blocking = ハードウェアの同時更新セマンティクス**。物理的なフリップフロップは、クロックエッジで全部同時に更新される。それを正しくモデル化するのが `<=` なんだ」

「では `=` はいつ使いますの？」

「**組合せ論理** を `always @(*)` で書くときだけ。あるいは、テストベンチで時間順に手続きを書くとき。**FF の記述には絶対に使わない**」

桃華は『同時シャッターで撮った集合写真』を思い浮かべた。全員が同じ瞬間に微笑む。その瞬間を切り取ったのが `<=` だ。

> **作法 6.** FF を記述する `always @(posedge clk ...)` では non-blocking ( `<=` ) を使う。blocking ( `=` ) は組合せ論理用。

---

## § 7. ビット幅は数学 — `23'd0` の作法

```verilog
counter <= 23'd0;
```

「桃華さん。これを声に出して読むと？」

「23 ビット幅の、10 進数の 0、ですわ」

「正解。じゃあ、こう書いたら何が起きる？」

```verilog
counter <= 0;
```

「えっと……同じことでは……?」

「結果は同じになる **ことが多い**。でも保証されない」とありすは静かに言った。「Verilog では、ビット幅を省略すると **32 ビット整数** として扱われる。それを 23 ビットの `counter` に代入すると、上位 9 ビットが切り捨てられる」

「実害は……?」

「比較式で問題が出る。例えば」

```verilog
if (counter < 6_749_999)        // 32 ビット同士の比較
if (counter < 23'd6_749_999)    // 23 ビット同士の比較
```

「シミュレータと合成ツールで挙動が微妙に変わる場合がある。**作法として、リテラルにはビット幅を書く**」

「`1'b1` と書くのも同じ理由ですのね」

```verilog
counter <= counter + 1'b1;      // 1 ビットの 1
counter <= counter + 1;         // 32 ビットの 1（暗黙的に拡張される）
```

「形式上は両方動くけど、明示する方が **意図が読める**」

「ふぁ、数値の途中の `_` は……?」

「単なる可読性のためのセパレータ。`6_749_999` は人間が読みやすい。Verilog はこれを無視して `6749999` として扱う」

「数学のカンマと同じですわね、6,749,999」

> **作法 7.** リテラルにはビット幅と基数を書く（`23'd0`, `1'b1`, `8'hff`）。長い数値は `_` で 3 桁区切り。

---

## § 8. 組合せ論理と順序論理 — `assign` と `always` の住み分け

```verilog
assign led = ~led_count;
```

「最後はこの行だ」とありすは画面を指した。「`assign` は何を意味する？」

「ええと……右辺を左辺に常に代入する、ですわ」

「半分正解。正確には、**右辺を左辺に常に結線する**。`assign` は **組合せ論理** の宣言なんだ」

ありすはホワイトボードに NOT ゲートを 6 つ描いた。

```
led_count[0] --|>o-- led[0]
led_count[1] --|>o-- led[1]
led_count[2] --|>o-- led[2]
led_count[3] --|>o-- led[3]
led_count[4] --|>o-- led[4]
led_count[5] --|>o-- led[5]
```

「`assign led = ~led_count;` は、この回路を 1 行で書いたものに等しい。**クロックは必要ない**。`led_count` が変わった瞬間、`led` も変わる」

「もし `always` で書くなら……?」

```verilog
always @(*) begin
    led_reg = ~led_count;
end
assign led = led_reg;
```

「こうも書ける。`always @(*)` の `*` は『右辺に出てくる全変数』を自動的に感度リストに入れる、という記法。これも組合せ論理だ。ただし、こんな単純な反転には冗長すぎる」

「`assign` のほうが、すっきりしていて分かりやすいですわね」

「うん。**1 行で書ける組合せ論理は `assign`、複雑なロジックは `always @(*)`、状態を持つものは `always @(posedge clk ...)`**。3 種類の使い分けが Verilog の基本リズム」

| 書き方 | 用途 | 例 |
|--------|------|----|
| `assign` | 単純な組合せ論理 | `assign y = a & b;` |
| `always @(*)` | 複雑な組合せ論理 | case 文を含むデコーダ |
| `always @(posedge clk ...)` | 順序論理（FF） | カウンタ、レジスタ |

> **作法 8.** 組合せ論理は `assign` か `always @(*)`、順序論理は `always @(posedge clk ...)` で書き分ける。混在させない。

```

**問題 2.** 次のコードを `parameter` 化して、点滅周期を外部から変更できるようにせよ。

reg [22:0] cnt;

```

**問題 3.** 次の 2 つの記述は、合成結果がどう違うか?

```verilog
// A

always @(posedge clk) begin
    a <= b;

```
